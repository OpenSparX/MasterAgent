# MasterAgent 项目目录整改与配置包迁移计划

## 1. 结论

当前代码已经具备 MasterAgent 内核模块、完整单进程组合根、开发者 CLI、模型 Runtime Adapter 和部分配置化能力，但存在三套并行的配置概念：

1. `config/`：C++ Prompt/Skill 引擎当前实际读取的旧配置。
2. `agent.yaml + skills/`：`sparx init/run/add/deploy` 当前实际读取的开发者项目格式。
3. `agent-config/`：新建的 MasterAgent 配置包目标协议，可表达 Rule、Skill、Capability、ContextSource、SubAgent、Model、Policy 和测试，但尚未由 Runtime 统一加载。

整改不应是简单“换目录名”，而应以 `agent-config` 作为唯一用户配置面，以编译后的不可变 `ConfigSnapshot` 作为 Runtime 唯一配置入口。在完成这条链路前，不删除当前仍在运行的旧文件。

## 2. 整改目标和边界

整改后要达到：

- 用户只需替换或切换一个 MasterAgent 配置包。
- 端侧意图模型、端侧分类模型、云端模型与端云路由都跟随配置包。
- 模型、Rule 和云端输出都生成统一 Decision，由本地 Validator 校验后才能执行。
- 内核模块不直接解析多份 YAML，只读已校验、已解析引用、已计算摘要的快照。
- 大模型权重和 API 密钥不进 Git，只在启动时通过外部引用解析。
- 开发者工具、具体 Adapter 和 Kernel/Core 边界清晰。

配置可以选择已注册代码，但不能带入任意脚本、动态库、未注册 URL，也不能覆盖权限、幂等、WAL、fencing、取消和对账底线。

├── scripts/                    # 仓库工具
│   ├── config/                # 新增：配置校验、编译、迁移
│   ├── release/               # 逐步归类已有发布脚本
│   └── tests/                 # CLI/安装/打包端到端测试
├── src/                        # Core 实现
│   ├── config/                # 新增：快照加载、引用解析、摘要和激活
│   ├── decision/              # 新增：统一 IR 校验和现有 DAG 转换

`adapters/` 是目标目录，不在第一步空建大量文件夹。等移动 llama.cpp Adapter 时再与可独立编译的 CMake target 一起建立，避免只做表面整齐。

## 5. 配置包内每个目录的作用

| 资源 | 职责 | 不能做的事 |
| --- | --- | --- |
| `manifest.yaml` | 配置包身份、版本、资源入口、兼容性、默认选择和完整性策略 | 不存放权重或密钥 |
| `rules/` | 明确请求的确定性匹配、槽位归一化和 Decision 模板 | 不绕过 Validator 直接执行 |
| `skills/` | 任务知识、触发语义、允许的信息源/能力/SubAgent | 不创造新执行器 |
| `capabilities/` | 可调用 Tool 的输入输出、副作用、权限、幂等、超时和 Provider 约束 | 不实现 Provider 代码 |
| `context_sources/` | 记忆、车辆状态和其他只读证据源的新鲜度、权限、大小和上云约束 | 不包含写操作 |
| `agents/` | 可调度 SubAgent 的输入输出、权限、取消和完成证据 | 不接受无边界自由任务 |
| `models/` | 端侧/云端模型角色、Runtime、外部引用、参数、协议和评测门槛 | 不把权重、endpoint 密钥写入 Git |
| `policies/` | 权限、安全、端云路由、模型选择、deadline 和生产门槛 | 不覆盖代码强制安全底线 |
| `prompts/` | 系统指令和 Decision JSON 协议 | 不存放必须强制执行的权限规则 |
| `schemas/` | 资源与输入输出契约，默认字段闭集 | 不代替跨资源语义校验 |
| `tests/` | 配置包随包行为契约和模型协议用例 | 不调用生产真实副作用 |

## 6. 建议增加的代码

### 6.1 ConfigBundle 子系统

新增公开契约 `include/master_agent/config/`和实现 `src/config/`，分成四个明确职责：

- `BundleLocator`：按“显式 `--config` → 已激活包 → 项目官方包 → 安装内置包”解析路径。
- `BundleCompiler`：解析 YAML/JSON/Markdown，校验 Schema、ID、引用、冲突和安全约束，生成规范 JSON 快照。
- `ExternalReferenceResolver`：在启动时解析权重路径、endpoint 和凭证；只返回脱敏元数据给日志。
- `ConfigSnapshotStore`：管理摘要、不可变快照、原子激活和回滚，每个请求冻结一份快照。

不建议让所有 Core 模块各自读 YAML，否则引用解析、字段默认值和更新时序会分裂。

本轮已先增加 `model_profile_loader` 作为最小 Runtime 切片：它从 Manifest、`models/` 和 ModelRoutingPolicy 解析端侧 intent/classifier 与云端选择，并对未知、禁用或不支持的显式选择失败关闭。它不是通用 YAML 引擎，将在完整 BundleCompiler/ConfigSnapshot 落地后被规范解析结果替换。

### 6.2 统一 Decision 子系统

新增 `include/master_agent/decision/` 和 `src/decision/`，承载：

- `Reply`、`Ask`、`QueryBatch`、`ExecutionPlan`、`RequestCloud`、`Fail` 六类 Decision。
- `CallTool`、`CallAgent` 等 Action 的字段闭集。
- Rule 输出、端侧模型输出、云端模型输出的统一 Validator。
- 与当前 `IntentOutcome` 和 Orchestrator DAG 的过渡转换器。

### 6.3 Adapter Registry

新增类型化注册表，使配置只能选择已编译或已安装的 Adapter：

- `ModelRuntimeRegistry`：`deterministic_mock`、`llama_cpp`、`qnn_genie`、`openai_compatible`。
- `CapabilityProviderRegistry`：Capability ID 到可信 Provider 的绑定。
- `SubAgentRegistry`：Agent ID 到调度 Adapter 的绑定。

如果配置显式选择了未注册 Adapter，启动必须失败，不能悄悄换成 Mock。

### 6.4 CLI 命令

增加以下用户闭环：

- `sparx config init <directory>`
- `sparx config validate <directory>`
- `sparx config compile <directory>`
- `sparx config use <directory>`
- `sparx config current`
- `sparx config pack <directory>`
- `sparx run --config <directory> [--model-profile <id>]`

`--model <gguf>` 作为开发调试快捷覆盖可暂时保留，它只覆盖 ModelProfile 的权重路径，不覆盖协议、权限、端云策略和执行能力。

不应删除的是 Orchestrator、AtomicService、Inference、Memory、DataLog、Exception 等内核模块。配置化的目的是向它们提供可版本化的输入，不是用 YAML 代替可靠执行机制。

## 9. 私有头文件目录的整理

当前多个模块使用 `src/<module>/include/` 存放私有头文件，并在 `.cpp` 中以 `#include "include/..."` 引用。这些头文件并没有作为 PUBLIC include directory 安装，名称容易让人误以为它们是 SDK API。

建议逐模块把它们改为 `src/<module>/internal/`，并改用 `#include "internal/..."`。这是机械性迁移，应每次只处理一个模块并立即编译，不与 Decision/Config 功能改造混在同一提交。

## 10. 迁移顺序

### 阶段 A：配置协议与模型选择基线（本轮）

- 补齐官方 `agent-config`，新增端侧/云端 ModelProfile 与 ModelRoutingPolicy。
- 模型权重、endpoint 和凭证采用外部引用。
- 扩展配置校验器，检查 Model ID、role/location、默认路由、Prompt/Schema 和测试集引用。
- 完整 `master_agent` 支持 `--config`/`--model-profile`，可根据 ModelProfile 选择端侧 Mock 或 llama.cpp，并从外部引用解析 GGUF 路径/endpoint。
- 将旧 `config/` 标记为 Legacy，冻结新功能进入。

验收：配置包基础校验、CMake 构建、CTest 和安装资源检查通过。

### 阶段 B：可加载的 ConfigSnapshot

- 实现 `validate/compile/run --config`。
- Runtime 先从快照获取 Prompt、Skill 和 ModelProfile，其他目录仍保留现有代码注册。
- 明确 CLI override > 配置包 > 安装默认值的优先级，显式无效值 fail-closed。

验收：复制官方包、修改 Qwen 权重引用后，不改 C++ 即可启动完整 MasterAgent；切换第二个包时旧快照可回滚。

### 阶段 C：统一 Decision 和 climate 垂直闭环

- 实现 Decision Validator 和现有 DAG 转换。
- 将循环模式、自动风速硬编码迁入 RuleCatalog。
- 端侧 Qwen 只输出有限 Decision；不再直接把自由文本当执行结果。
- 云端输出返回本地 Validator。

验收：明确指令经 Rule 执行；模糊指令经本地模型和状态接口产生可校验 Action；端侧不足才可申请上云。

### 阶段 D：唯一配置面和目录物理整理

- `sparx init/add/deploy` 转为配置包。
- 将具体 Model Runtime 移到 `adapters/models/`。
- 将私有头文件的 `include/` 改名为 `internal/`。
- 在 Legacy 等价测试后删除 `config/`、旧解析器和重复 Skill 路径。

验收：仓库中只有一套用户配置概念；旧格式仅由独立迁移工具支持。

## 11. 提交和回滚策略

建议按以下粒度提交，不要做一个同时移动数百文件又改行为的大提交：

1. 官方配置包、Schema、校验器和文档。
2. ConfigSnapshot 数据结构和纯解析测试。
3. Prompt/Skill 读快照和 Legacy 对等测试。
4. ModelRuntimeRegistry 和 `--model-profile`。
5. 统一 Decision Validator。
6. climate Rule 迁移。
7. 云端 ModelProfile 和真 Adapter。
8. 纯目录移动（Adapter、私有头文件）。

每个提交都应保持可编译、可测试、可单独回滚。

## 12. 本轮实际落地与未落地边界

本轮已落地的是：

- `agent-config/models/` 及默认 ModelRoutingPolicy。
- Qwen2.5-3B GGUF、端侧 Mock、Mock classifier、Fake Cloud 和 OpenAI-compatible 云模型的声明。
- ModelProfile/ModelRoutingPolicy Schema 基线和模型协议测试资源。
- 配置校验器的模型引用、路由、协议和测试集检查。
- `master_agent --config=<bundle> [--model-profile=<id>]` 的模型选择切片，支持当前 Mock 和 llama.cpp Runtime，显式无效选择不静默降级。
- 真实 Qwen 验证暴露的“无执行回执却用 REPLY 声称已调整设备”已在本地校验层拦截为 `INTENT_MODEL_FALSE_EXECUTION_CLAIM`。
- Qwen2.5-3B 的 llama.cpp 真实推理、REAL 轨迹和 ModelProfile ID 绑定已验证；它对现有严格两阶段 JSON 协议仍会产生非法输出，因此标记为 experimental，不宣称已达生产可用。
- 旧 `config/` 的 Legacy 说明和可删除门槛。

本轮没有宣称已落地的是：

- Runtime 当前只加载 `agent-config` 的模型选择切片，尚未把 Rule、Skill、Capability、ContextSource、Agent、Prompt 和全部 Policy 编译为 ConfigSnapshot。
- `sparx config ...`、`sparx run --config`、`sparx --model-profile` 仍是下一阶段产品接口；当前是完整 `master_agent` 参考应用提供 `--config`/`--model-profile`。
- `adapters/`、`src/config/`、`src/decision/` 将在有真实实现与测试时创建，本轮不创建空架子。
- 旧 `config/`、`agent.yaml` 和 CLI 内 Adapter 尚未删除，因为当前真实运行和测试仍依赖它们。

这个边界非常重要：目录设计文档可以先冻结目标，但只有编译、加载、运行和回滚测试通过后，才能把“计划删除”变成“真实删除”。
