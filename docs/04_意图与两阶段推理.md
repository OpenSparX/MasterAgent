# 意图识别与两阶段推理

## 1. 确定性优先

Intent 首先调用确定性解析适配器：

- 问候、感谢等直接生成 `REPLY`。
- 参数缺失生成 `ASK`。
- 能力和参数完整生成确定性 `PLAN`。
- 只有规则不能闭合时才进入模型路径。

因此反问和回复都属于确定性终态，不需要进入任务编排引擎。

独立 Skill 引擎负责加载、检索和渐进披露纯文本 Skill 库，不直接执行工具，也不承担确定性参数闭合。Intent 通过 `intent_support` 适配层组合 Skill 候选、MCP 工具和确定性规则，避免改变 Skill 模块负责人提供的公共接口与实现。

## 2. 第一阶段输入

独立 Prompt 引擎按 `config/prompt/templates.json` 选择模板、替换槽位并生成基础文本。Intent 的 Prompt 适配器在基础文本之外封装以下模型协议内容：

- 系统约束。
- MCP Tool 能力摘要。
- 脱敏短期上下文。
- 用户规范化输入。
- 封闭输出协议。

示例：

```text
SYSTEM:
你是车端 Master Agent 意图编排器。只能输出受控 JSON...
TOOLS:
[{"name":"com_sgm_service_climate_setAutoFanSpeed", ...}]
MEMORY:
用户通常优先选择公共交通
USER:
请按我的历史偏好规划明天行程
PROTOCOL:
FIRST_INFERENCE must return QUERY_BATCH or NO_QUERY...
```

第一阶段输出只能是：

```json
{
  "branch": "QUERY_BATCH",
  "queries": [
    {
      "query_id": "q1",
      "source": "memory",
      "operation": "get_preferences",
      "arguments": {}
    }
  ]
}
```

或直接闭合：

```json
{
  "branch": "NO_QUERY",
  "final": {
    "outcome": "ASK",
    "reply": "请确认你希望采用哪一种偏好。"
  }
}
```

## 3. 第二阶段输入

只有第一阶段返回完整 `QUERY_BATCH` 时才执行查询。查询结果被冻结成 EvidenceBundle：

```json
{
  "query_batch": [{"query_id":"q1","source":"memory"}],
  "results": [
    {"query_id":"q1","status":"OK","evidence":{"preference":"public_transit"}}
  ]
}
```

第二阶段接收第一阶段 Prompt 加 EvidenceBundle，只能输出最终 `PLAN`、`ASK`、`REPLY` 或 `FAIL`，不能继续请求查询。

```json
{
  "outcome": "PLAN",
  "plan": {
    "nodes": [
      {
        "node_id": "trip-plan",
        "executor": "agent_dispatch",
        "action": "com_sgm_agent_trip_plan",
        "dependencies": []
      }
    ]
  }
}
```

## 4. 输出去向

- `PLAN`：进入任务编排引擎。
- `ASK`、`REPLY`、`FAIL`：经 AgentService 直接返回交互接入层。
- 模型原始输出：先经过 JSON、枚举、字段、长度、能力和 DAG 校验，不能直接返回用户或调用 Tool。

Mock Runtime 记录阶段、Prompt 摘要、原始模拟输出、输出摘要和 `SIMULATED` 标记，便于测试两阶段边界。
