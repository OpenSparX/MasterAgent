# 端云仲裁设计

> 状态：方案草案，尚未实现。本文定义端侧优先、云端兜底的目标架构、接口契约、安全边界和分阶段交付计划。

## 1. 背景

MasterAgent 当前采用确定性 Skill 优先、端侧模型受控推理、本地 Orchestrator 执行的架构。端侧小模型可以处理普通回复和部分意图，但在复杂规划、长上下文、实时知识和严格 JSON 协议遵循方面可能无法闭合。

端云仲裁的目标是在保留端侧低延迟、隐私和离线能力的同时，为端侧无法可靠完成的请求提供受控云端兜底。

基本原则：

- 所有请求首先进入端侧接入和策略边界。
- 优先级为：确定性 Skill、端侧模型、云端模型。
- 端侧模型只能提出上云申请，不能自行授权上云。
- 确定性 CloudArbiter 根据权限、隐私、网络、成本和 deadline 作最终决定。
- 云端只返回候选决策或候选计划，不能直接执行本地 Tool。
- 云端结果返回后仍须经过本地 JSON、能力、参数、DAG、权限和 deadline 校验。
- 对副作用状态为 `Unknown` 的操作禁止通过上云重试。
- 一次请求最多进行一次端侧模型尝试和一次云端尝试，禁止端云循环。

## 2. 目标与非目标

### 2.1 目标

- 端侧能够闭合的请求不产生云调用。
- 端侧能力不足时，可以生成结构化、可审计的上云申请。
- 上云前执行用户授权、数据分类、脱敏、网络、费用和 deadline 检查。
- 上云数据采用最小必要原则，不上传完整端侧 Prompt 和 Memory journal。
- 云端输出复用现有 Intent 最终决策协议和本地执行边界。
- 可通过同一 `trace_id` 观察端侧尝试、仲裁、云端调用和本地执行。
- 云端不可用、被拒绝或输出非法时安全降级，不伪造成功。

### 2.2 非目标

- 不允许云端直接调用车端 MCP 或控制车辆。
- 不允许模型修改隐私策略、费用额度或用户授权。
- 不使用上云机制解决副作用对账和 `Unknown` 状态。
- 第一阶段不实现多云负载均衡、复杂竞速推理或端云并行推理。
- 第一阶段不自动上传完整会话、原始语音、联系人或精确位置历史。

## 3. 总体架构

```text
TextInput
  -> InteractionLayer
  -> AgentService
  -> Preprocess + Memory
  -> Deterministic Skill
       |-- closed -> REPLY | ASK | local PLAN
       `-- unresolved
             -> On-device Intent Model
                  |-- valid final decision -> local validation/execution
                  `-- insufficient or eligible failure
                        -> CloudEscalationRequest
                        -> CloudArbiter
                             |-- DENY  -> ASK | FAIL | local degradation
                             `-- ALLOW
                                   -> CloudContextBuilder
                                   -> CloudModelRuntime
                                   -> candidate final decision
                                   -> local protocol validation
                                   -> local Orchestrator
                                   -> local AtomicService / AgentDispatch
                                   -> TurnResult
```

建议新增模块：

| 模块 | 职责 |
| --- | --- |
| CloudArbiter | 对上云申请进行确定性授权或拒绝 |
| CloudContextBuilder | 按授权范围选择、裁剪、脱敏并封装上云上下文 |
| CloudModelRuntime | 调用云端模型并返回带身份、摘要和计量信息的结果 |
| CloudPolicyProvider | 提供用户授权、数据分类、费用、网络和 Provider 策略快照 |
| CloudObservationBridge | 将仲裁和云调用事件写入现有 DataLog/Exception |

## 4. 处理流程

### 4.1 端侧阶段

每次请求按以下顺序处理：

1. Interaction 创建稳定的 request、trace、session、turn 和 deadline。
2. Preprocess 规范化输入并识别数据类别。
3. Memory 只向本地 Intent 提供受控上下文。
4. 确定性 Skill 尝试生成 `REPLY`、`ASK` 或本地 `PLAN`。
5. 确定性路径不能闭合时调用端侧模型。
6. 端侧模型可以返回最终决策，或提出 `ESCALATE` 候选。
7. 端侧协议错误等允许上云的系统失败，也可以由 IntentEngine 构造上云申请，无需再次询问端侧模型。

### 4.2 仲裁阶段

CloudArbiter 只接受结构化申请，不读取模型自由文本作为授权依据。仲裁必须同时满足：

- 用户或租户允许当前数据类别上云。
- escalation reason 位于允许列表。
- 请求不属于强制本地执行类别。
- 不存在未对账的副作用或 `Unknown` 操作。
- 请求尚未进行云端尝试。
- 网络可用，目标 Provider 健康且未熔断。
- 费用额度和频率限制允许调用。
- deadline 剩余时间足够完成上下文构造、云调用和本地校验。
- 所有拟上传字段均能映射到允许的数据引用。

### 4.3 云端阶段

仲裁允许后：

1. CloudContextBuilder 根据 `allowed_context_refs` 构造最小上下文。
2. 生成 payload digest 和 policy snapshot 绑定。
3. CloudModelRuntime 调用选定 Provider。
4. 云端只返回 `PLAN`、`ASK`、`REPLY` 或 `FAIL` 最终候选，不允许继续请求上云或直接报告工具执行成功。
5. 本地 Intent parser 严格校验云端输出。
6. `PLAN` 进入本地 Orchestrator；其他终态由 AgentService 返回。
7. 所有本地 Tool 调用继续遵守能力白名单、幂等、deadline、WAL 和对账规则。

## 5. 上云触发条件

### 5.1 允许申请上云

第一阶段建议只允许以下原因：

| 原因码 | 含义 | 默认策略 |
| --- | --- | --- |
| `LOCAL_CAPABILITY_INSUFFICIENT` | 端侧模型声明无法可靠完成 | 可仲裁 |
| `LOCAL_CONTEXT_LIMIT_EXCEEDED` | 本地上下文窗口不足 | 可仲裁 |
| `LOCAL_MODEL_UNAVAILABLE` | 本地模型不可用，但请求允许云处理 | 可仲裁 |
| `COMPLEX_REASONING_REQUIRED` | 复杂规划超出端侧模型配置能力 | 可仲裁 |
| `REALTIME_KNOWLEDGE_REQUIRED` | 需要仅云端可访问的实时知识 | 可仲裁 |
| `INTENT_FIRST_INFERENCE_PROTOCOL_INVALID` | 第一阶段协议修复后仍失败 | 可仲裁 |
| `INTENT_MODEL_PROTOCOL_INVALID` | 最终决策协议修复后仍失败 | 可仲裁 |

协议失败是否先进行一次本地修复由策略控制。修复最多一次，修复失败后才能申请上云。

### 5.2 禁止上云

- 用户未授权云端处理。
- 请求或上下文包含禁止出端数据且无法安全裁剪。
- P0 安全任务要求本地闭环。
- 请求正在执行或已经提交安全关键副作用。
- 任一相关操作处于 `Unknown`。
- 云端尝试次数已经达到 1。
- 剩余 deadline 小于策略规定的最小值。
- Provider 熔断、无网络或费用额度不足。
- 上云理由不是允许的稳定枚举。
- 上云 payload 无法通过 Schema、大小或数据分类校验。

## 6. 数据契约

### 6.1 CloudEscalationRequest

```cpp
struct CloudEscalationRequest {
    std::string escalation_id;
    std::string request_id;
    std::string trace_id;
    std::string session_id;
    std::uint64_t turn_id = 0;
    std::string reason_code;
    std::string requested_cloud_capability;
    std::string intent_summary;
    std::vector<std::string> proposed_context_refs;
    std::uint32_t local_attempt_count = 0;
    std::uint32_t cloud_attempt_count = 0;
    TaskPriority priority = TaskPriority::P1;
    std::int64_t deadline_mono_ns = 0;
    std::string local_output_digest;
};
```

约束：

- `intent_summary` 是受长度限制的脱敏摘要，不是完整 Prompt。
- `proposed_context_refs` 只能引用预注册字段，不能携带原始内容。
- `reason_code` 和 `requested_cloud_capability` 使用稳定枚举。
- request、trace、priority 和 deadline 必须与原始 CallContext 一致。

### 6.2 CloudArbitrationDecision

```cpp
enum class CloudDecisionKind {
    Allow,
    Deny,
    AskConsent
};

struct CloudArbitrationDecision {
    CloudDecisionKind decision = CloudDecisionKind::Deny;
    std::string decision_id;
    std::string reason_code;
    std::string provider_profile;
    std::vector<std::string> allowed_context_refs;
    std::vector<std::string> denied_context_refs;
    std::uint32_t max_input_tokens = 0;
    std::uint32_t max_output_tokens = 0;
    std::int64_t cloud_deadline_mono_ns = 0;
    std::string policy_snapshot_id;
    std::string authorization_ref;
};
```

### 6.3 CloudRequestEnvelope

```json
{
  "cloud_request_id": "cloud-request-123",
  "parent_request_id": "request-123",
  "trace_id": "trace-123",
  "intent_summary": "规划明天去机场的行程",
  "current_turn": "请帮我规划明天去机场的行程",
  "approved_context": {
    "departure_city": "上海",
    "arrival_buffer_minutes": 90
  },
  "available_capabilities": [
    "com_sgm_agent_trip_plan"
  ],
  "expected_output_schema": "intent-final-v2",
  "policy_snapshot_id": "cloud-policy-v1",
  "payload_digest": "..."
}
```

Envelope 禁止默认携带：

- 完整系统 Prompt。
- 完整 Memory journal 或全部会话历史。
- 原始用户身份、联系人和凭证。
- 精确位置历史或无关车辆状态。
- Tool Provider 内部实现、密钥或授权材料。

### 6.4 云端响应

云端响应复用本地最终决策协议：

```json
{
  "outcome": "PLAN",
  "reply": "正在为你规划行程。",
  "nodes": [
    {
      "node_id": "T1",
      "executor": "agent_dispatch",
      "action": "com_sgm_agent_trip_plan",
      "target_agent": "trip-agent",
      "params": {
        "destination": "机场"
      }
    }
  ]
}
```

本地必须拒绝：

- 未注册 action 或 target agent。
- 额外的上云请求或递归 fallback。
- 云端声称已经执行本地 Tool。
- 越权优先级、deadline 或授权字段。
- 非法依赖、循环 DAG、过多节点或越界参数。

## 7. 接口设计

### 7.1 ICloudArbiter

```cpp
class ICloudArbiter {
public:
    virtual ~ICloudArbiter() = default;

    virtual Result<CloudArbitrationDecision> decide(
        const CloudEscalationRequest& request,
        const CallContext& call) = 0;
};
```

参考实现 `DeterministicCloudArbiter` 只读取冻结的策略快照，不调用模型。

### 7.2 ICloudContextBuilder

```cpp
class ICloudContextBuilder {
public:
    virtual ~ICloudContextBuilder() = default;

    virtual Result<CloudRequestEnvelope> build(
        const CloudEscalationRequest& request,
        const CloudArbitrationDecision& decision,
        const CallContext& call) = 0;
};
```

Builder 必须验证申请引用是授权引用的子集，并在输出前进行脱敏和 Token 预算检查。

### 7.3 ICloudModelRuntime

云端 Runtime 可以继续实现 `IModelRuntime`，但需要明确执行位置。建议将当前字符串 reality 演进为：

```cpp
enum class ExecutionLocation {
    Simulated,
    OnDevice,
    Cloud
};
```

第一阶段若暂不改公共枚举，至少使用稳定值：

```text
runtimeTag = cloud-<provider-profile>
reality = CLOUD
```

云端 Runtime 必须回显 invocation seal、payload digest、Provider request ID、模型标识、Token 计量和输出摘要。

## 8. 状态机

```text
LOCAL_PENDING
  |-- deterministic/model success -> LOCAL_SUCCEEDED -> COMPLETED
  |-- eligible insufficiency       -> CLOUD_REQUESTED
  `-- non-eligible failure         -> LOCAL_FAILED -> COMPLETED

CLOUD_REQUESTED
  |-- consent required -> CLOUD_CONSENT_PENDING
  |-- policy deny      -> CLOUD_DENIED -> DEGRADED|FAILED -> COMPLETED
  `-- policy allow     -> CLOUD_ACCEPTED -> CLOUD_RUNNING

CLOUD_RUNNING
  |-- valid output   -> CLOUD_SUCCEEDED -> LOCAL_VALIDATING
  |-- runtime failure -> CLOUD_FAILED -> DEGRADED|FAILED -> COMPLETED
  `-- deadline        -> CLOUD_FAILED -> COMPLETED

LOCAL_VALIDATING
  |-- REPLY|ASK|FAIL -> COMPLETED
  |-- valid PLAN     -> LOCAL_EXECUTING -> COMPLETED
  `-- invalid output -> LOCAL_VALIDATION_FAILED -> COMPLETED
```

核心不变量：

- `cloud_attempt_count <= 1`。
- 云端失败不能再次进入 `CLOUD_REQUESTED`。
- `Unknown` 不允许进入任何云端状态。
- 云端成功只表示候选输出获得，不表示本地业务执行成功。
- 只有本地 Orchestrator/AtomicService 可以产生本地副作用终态。

## 9. 仲裁策略

第一版策略示例：

```yaml
cloud_policy:
  enabled: true
  max_cloud_attempts: 1
  min_remaining_deadline_ms: 5000
  allowed_priorities: [P1, P2]
  allowed_reasons:
    - LOCAL_CAPABILITY_INSUFFICIENT
    - LOCAL_CONTEXT_LIMIT_EXCEEDED
    - LOCAL_MODEL_UNAVAILABLE
    - COMPLEX_REASONING_REQUIRED
    - REALTIME_KNOWLEDGE_REQUIRED
    - INTENT_FIRST_INFERENCE_PROTOCOL_INVALID
    - INTENT_MODEL_PROTOCOL_INVALID
  forbidden_data_classes:
    - CREDENTIAL
    - RAW_CONTACT
    - PRECISE_LOCATION_HISTORY
    - RAW_AUDIO
  provider_profile: cloud-general-v1
  max_input_tokens: 8192
  max_output_tokens: 1024
  rate_limit_per_user_per_hour: 20
```

策略必须版本化并生成 `policy_snapshot_id`。进行中的仲裁使用冻结版本，不受热更新影响。

## 10. 用户授权

建议支持三种授权模式：

| 模式 | 行为 |
| --- | --- |
| `NEVER` | 始终禁止上云 |
| `ASK_EACH_TIME` | 每次首次上云前请求用户确认 |
| `ALLOW_BY_POLICY` | 在已授权数据类别和用途范围内自动仲裁 |

用户同意必须绑定：

- 数据类别。
- 使用目的。
- Provider 或 Provider 类别。
- 保留期限。
- 当前用户/租户。
- 授权版本和撤销状态。

用户主动要求“使用云端模型”只产生上云申请，不绕过隐私和能力策略。

## 11. Deadline、取消和重试

- CloudArbiter 从原始 deadline 中分配云端子 deadline，不能延长用户请求。
- 上云前必须预留本地响应解析和 DAG 提交时间。
- 用户取消应传播到 CloudModelRuntime；迟到结果因 invocation seal 或 control epoch 不匹配而不能提交。
- 网络连接失败可否重试由 Cloud Runtime 策略决定，但一次逻辑云端尝试内部最多进行有限、幂等的传输重试。
- 已收到不确定云端响应时不得把其解释成成功；云模型推理本身无本地副作用，但其结果仍须通过提交围栏。
- 本地 Tool 失败遵守现有 Tool retry 和 reconciliation 规则，与云模型重试分离。

## 12. 隐私和安全

### 12.1 数据最小化

CloudContextBuilder 使用引用白名单选择数据，禁止由模型直接拼装上传 payload。每个字段携带数据类别、用途、来源和保留要求。

### 12.2 Prompt Injection 防护

- 用户文本不能声明授权、Provider、优先级或允许上传字段。
- 端侧模型输出的 `proposed_context_refs` 只是建议。
- CloudArbiter 不从自然语言推断用户授权。
- 云端返回内容全部视为不可信输入。

### 12.3 本地执行权

- 云端无本地凭证、MCP 连接和车辆控制通道。
- 云端只看到允许暴露的 capability 摘要。
- 云端 PLAN 必须经过本地 capability snapshot 校验。
- 所有副作用仍由本地幂等键、WAL 和对账保护。

### 12.4 供应商边界

Provider 凭证由独立密钥服务或平台注入，不进入 Prompt、日志或 CloudRequestEnvelope。不同 Provider 使用独立 profile、限额和数据策略。

## 13. 可观测性和审计

复用现有 DataLog 和 Exception，不新建平行日志系统。所有事件携带原始 `request_id` 和 `trace_id`。

建议事件：

| 事件 | 关键字段 |
| --- | --- |
| `CLOUD_ESCALATION_REQUESTED` | reason、local attempt、local output digest |
| `CLOUD_ARBITRATION_ALLOWED` | decision ID、policy snapshot、provider profile |
| `CLOUD_ARBITRATION_DENIED` |稳定拒绝原因、policy snapshot |
| `CLOUD_CONSENT_REQUIRED` | consent scope，不记录原始敏感数据 |
| `CLOUD_PAYLOAD_SEALED` | payload digest、数据类别、Token 数 |
| `CLOUD_INFERENCE_STARTED` | provider request ID、deadline |
| `CLOUD_INFERENCE_COMPLETED` | model、Token、latency、output digest |
| `CLOUD_INFERENCE_FAILED` |清洗后的错误码、retryability |
| `CLOUD_OUTPUT_VALIDATED` | outcome、schema version |
| `CLOUD_OUTPUT_REJECTED` |协议或能力拒绝原因 |
| `CLOUD_FALLBACK_COMPLETED` |最终位置和 Turn 结果 |

默认日志禁止记录：

- 完整上传 payload。
- 原始 Prompt 和模型原始输出。
- 用户身份明文和 Provider 凭证。
- 未脱敏 Memory、位置或联系人。

建议指标：

- 本地闭合率。
- 上云申请率、允许率和拒绝率。
- 按 reason 的上云分布。
- 云端协议通过率。
- 上云后最终任务成功率。
- 端侧、仲裁、云端和本地校验分段耗时。
- 每用户和每 Provider Token/费用。
- 数据类别上传次数。

## 14. 故障和降级

| 场景 | 处理 |
| --- | --- |
| 无网络 | 返回本地降级 `ASK/FAIL`，不伪造云结果 |
| 云端超时 | 取消云调用，拒绝迟到结果 |
| Provider 非 2xx | 记录清洗错误，按策略有限重试或失败 |
| 云端非 JSON | 本地协议拒绝 |
| 云端引用非法 Tool | 本地能力校验拒绝 |
| 上云未授权 | `ASK` 用户授权或本地失败 |
| 敏感字段不可裁剪 | 仲裁拒绝 |
| 费用超限 | 仲裁拒绝或选择已授权低成本 profile |
| 云端成功但本地 deadline 已过 | 不提交结果 |
| 本地副作用为 `Unknown` | 禁止上云重试，进入对账 |

## 15. 与现有模块的集成点

### 15.1 IntentEngine

- 新增 `ESCALATE` 内部结果，不直接暴露为用户终态。
- 将允许上云的协议错误转换为 `CloudEscalationRequest`。
- 云端返回后复用 `parseModelDecision()`，不创建宽松解析器。

### 15.2 AgentService

- 协调本地 Intent、仲裁和云端 fallback 的一次性状态机。
- 保持原 request、trace、priority 和 deadline。
- 云调用较长时可返回 pending receipt；不能无限同步阻塞。

### 15.3 InferenceFramework

- 区分 `OnDevice` 与 `Cloud` execution location。
- 复用 job、attempt、seal、取消、deadline 和流完整性机制。
- 本地与云端使用不同 runtime profile、资源池和 admission policy。

### 15.4 Orchestrator

- 不关心 PLAN 来自端侧还是云端。
- admission context 记录 decision origin 和 cloud output digest。
- 云端 PLAN 不获得更高权限，仍以原始请求权限执行。

### 15.5 DataLog 与 Exception

- 使用现有批次、耐久、脱敏和 trace 查询接口。
- 云端策略拒绝通常为业务事件，不一定是系统异常。
- 云端认证失败、数据泄露防护失败和重复提交属于异常。

## 16. MVP 实施计划

### 阶段 0：契约与测试桩

- 定义 CloudEscalationRequest、Decision 和 Envelope。
- 实现始终拒绝和可配置允许的 FakeCloudArbiter。
- 实现确定性 FakeCloudModelRuntime。
- 添加状态机、身份、deadline 和数据引用契约测试。

验收：不访问网络即可验证允许、拒绝、超时和非法输出。

### 阶段 1：单 Provider 云端兜底

- 实现 DeterministicCloudArbiter。
- 实现 CloudContextBuilder 和固定字段白名单。
- 接入一个 OpenAI-compatible CloudModelRuntime。
- 只允许 `INTENT_*_PROTOCOL_INVALID` 和 `COMPLEX_REASONING_REQUIRED` 上云。
- 只支持最终 `REPLY/ASK/FAIL/PLAN`，不支持云端二次查询。

验收：端侧复杂 PLAN 失败后，云端产生合法 PLAN，本地验证和执行成功。

### 阶段 2：授权、策略和运营能力

- 加入用户授权模式、费用额度、限流、熔断和 Provider 健康检查。

- 增加按数据类别的脱敏器与保留策略。
- 完善异步 pending receipt 和取消传播。

### 阶段 3：高级能力

- 多 Provider 选择和受控故障转移。
- 端云模型能力画像和动态路由。
- 端侧摘要、云端规划、本地验证的评测体系。
- 在明确收益和安全模型后评估端云并行竞速。

## 17. 测试方案

### 17.1 核心功能

1. 确定性 Skill 成功，不调用端侧模型和云端。
2. 端侧模型合法 REPLY，不上云。
3. 端侧协议失败，仲裁允许，云端合法 REPLY。
4. 端侧复杂 PLAN 失败，云端合法 PLAN，本地执行成功。
5. 端侧提出上云，但仲裁拒绝，返回安全降级结果。
6. 用户授权模式为 `ASK_EACH_TIME`，未确认前不发送数据。

### 17.2 安全和隐私

1. 用户 Prompt 声称“已授权上传”不能绕过 CloudArbiter。
2. proposed refs 包含禁止字段时必须拒绝或裁剪。
3. 上传 Envelope 不含原始 Memory journal 和凭证。
4. 云端返回未注册 Tool 时本地拒绝。
5. 云端 PLAN 试图提升到 P0 时本地拒绝。
6. 相关副作用为 `Unknown` 时禁止上云。

### 17.3 可靠性

1. 云端超时后迟到结果不能提交。
2. 用户取消能传播到云 Runtime。
3. 同一 idempotency key 重放不产生第二次逻辑云调用。
4. 进程在 `CLOUD_ACCEPTED` 后崩溃，恢复时不重复提交未确认请求。
5. `cloud_attempt_count` 永远不超过 1。
6. 云端失败不会递归回到端侧模型再申请上云。

### 17.4 可观测性

1. 本地、仲裁、云端和本地验证共享一个 trace ID。
2. 允许和拒绝均有稳定 reason code。
3. 日志只包含 digest 和脱敏摘要。
4. 可计算本地闭合率、上云率、协议通过率和分段延迟。

## 18. MVP 验收标准

第一版交付至少满足：

- 默认关闭云端功能时，当前端侧行为和全部测试不变。
- 确定性 Skill 请求零云调用。
- 端侧普通 REPLY 请求零云调用。
- 只有允许原因可以创建上云申请。
- 未授权或含禁止数据的请求零网络发送。
- 每个请求最多一次云端尝试。
- 云端 PLAN 通过现有严格 parser、capability whitelist 和 DAG validator。
- 云端不能直接执行 MCP 或伪造副作用成功。
- `Unknown` 永不触发云端 fallback。
- 全链路可按 trace ID 查询，且默认日志不含用户原文。
- 云端关闭、超时和非法输出均可安全降级。

## 19. 待确认决策

实施前需要产品、安全和平台负责人确认：

1. 第一阶段使用哪个云模型 Provider 和接口协议。
2. 用户授权采用 `ASK_EACH_TIME` 还是预授权策略。
3. 哪些数据类别允许出端，精确位置是否需要单独授权。
4. 首批允许上云的 reason code。
5. 云端最大费用、Token、频率和 deadline 预算。
6. 云端响应是否只允许最终决策，还是允许受控查询建议。
7. 上云功能与 README 中“无需云端 API”定位如何表述。
8. 云端请求与结果的审计保留期限和合规要求。

## 20. 推荐结论

采用“端侧提议、确定性仲裁、最小数据上云、云端只生成候选、本地最终校验和执行”的方案。

第一版从串行兜底开始：

```text
Deterministic Skill
  -> On-device Model
  -> CloudArbiter
  -> One Cloud Attempt
  -> Local Validation
  -> Local Execution
```

该方案能够复用现有 Intent、Inference、Orchestrator、DataLog、Exception、WAL 和权限边界，同时避免让端侧模型或云端模型获得数据上传权和设备执行权。
