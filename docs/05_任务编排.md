# 任务编排

## 1. 接受与执行分离

`IOrchestrator::submit()` 只确认计划是否通过校验并被可靠接收，不代表执行成功。调用方随后使用稳定 `plan_id` 查询状态。

## 2. DAG 校验

提交前校验：

- plan、node、edge 和幂等身份。
- 节点数量、依赖数量和 schema 上限。
- 无环性和依赖完整性。
- executor 只能是已知模块，例如 `atomic_service`、`agent_dispatch`。
- action 必须存在于冻结能力目录。
- P0 授权、deadline 和重试策略。
- 原子副作用重试必须具备可信幂等策略。

## 3. 状态

计划状态：

- `Committed`
- `Running`
- `Succeeded`
- `Failed`
- `Cancelled`
- `Unknown`

节点 Activation 记录 attempt、fencing token、control epoch、执行身份和副作用状态。状态只能单向推进；旧事件不能覆盖新状态。

## 4. 调度顺序

Ready 节点按优先级、deadline、稳定入队序号选择。依赖未完成的节点进入 BlockerIndex。资源不足时等待 Capacity，而不是忙重试 Provider。

## 5. Unknown 与对账

如果 Provider 调用已经开始，但完成回执丢失或恢复后无法证明结果，编排器不能把任务标记为成功或简单失败。节点进入 Reconciling，最终无法判定时计划进入 `Unknown`。

`Unknown` 是终态事实声明，不是普通错误码。重复提交相同副作用可能造成二次执行，因此必须通过执行 ID 和幂等账本对账。

## 6. 持久化

计划提交、关键状态、终态和恢复信息写入 WAL。恢复时：

- 已知终态直接重放。
- 未完成且没有可靠副作用证明的任务失败关闭。
- 损坏的已提交记录阻止继续接收工作。
- torn tail 可在明确边界内截断修复。
